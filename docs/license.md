# 许可说明：为什么"依赖"它，而不是"搬"它

> 这不是法律意见，是工程上的取舍说明。真要走分发/商用，请自行复核或咨询。

## 一、涉及的三个东西

| 东西 | 许可 | 我们怎么做 |
|---|---|---|
| [LearnHarness](https://github.com/amosblomqvist/learnharness)（上游应用，Next.js + Electron） | AGPL-3.0 | 不复制、不 fork。只读它的文档与源码来理解方法 |
| [`dsh-learnharness`](https://github.com/tianweichao/dsh-learnharness)（第三方 DSH 插件，教学法的移植） | AGPL-3.0 | **本仓库不包含它的代码**，独立安装 |
| 本仓库 `plugins/studyhub` | MIT | 我们自己写的 |

## 二、为什么不能"顺手放进来"

AGPL-3.0 是最强的 copyleft 之一。它的核心要求是：**你分发基于它的作品时，整个作品都得按 AGPL 授权，并且提供源码。**

如果把 `dsh-learnharness` 的代码（哪怕只是 `lib/*.js`）复制进本仓库一起发布，会发生：

1. 本仓库的分发**整体**要满足 AGPL —— 也就是说，你不能再只挂一个 MIT LICENSE 就完事；
2. 每个下载这个仓库的人，都获得 AGPL 赋予的权利（再分发、要求源码）；
3. 上游一更新，你得手动同步这份副本，否则慢慢腐烂。

一句话：**为了省一条安装命令，把 MIT 仓库变成 AGPL 项目，还背上同步负担——不划算。**

## 三、为什么"依赖"是安全的

我们和它的关系是**两个独立程序**：

- 没有 `import` / `require` 它的任何代码；
- 没有把它的文件打进同一份产物；
- 它在 DSH 里通过公开的扩展点注册工具，我们同样；两者只在**同一个运行时的工具表**里相遇；
- 数据上只共享一个目录 `~/.dsh/learn`（它也这样设计，见它的 README）。

这属于"在同一个平台上并列运行的两个程序"，而不是"基于它的改编作品"。所以本仓库可以保持 MIT。

> 注意：**自用完全不触发任何义务**。AGPL 约束的是"分发"。你一个人在自己机器上跑，装不装、改不改都没人管。

## 四、真正要留意的两件事

1. **不要把"组合"打包分发。** 如果你以后做了一个一键安装包、Docker 镜像、或者把两个插件捆在一起发出去，那个**组合**就落进 AGPL 的范围了 —— 那时你需要提供整个组合的源码与许可文本。
2. **别抄它的文案。** 方法、机制、思路不受版权保护（我们文档里大量引用它的三条机制，这没问题）；但它 `src/agent/prompts/` 里那 22 篇提示词的**文字**是它的作品，照抄进本仓库就是侵权。

## 五、如果你确实想 vendor（离线分发 / 锁版本）

可以，但要按下面的方式来，我可以帮你改：

```
dsh-study/
├─ LICENSE                      ← 保持 MIT，但加一句例外说明
├─ vendor/
│  └─ dsh-learnharness/
│     ├─ LICENSE                ← 它的 AGPL-3.0 原文，必须保留
│     ├─ NOTICE                 ← 版本号、来源 URL、上游 commit
│     └─ lib/...                ← 原样复制，不做修改
```

同时在根 README 的许可一节写明：

> 本仓库除 `vendor/dsh-learnharness/` 外均为 MIT。
> `vendor/dsh-learnharness/` 是 AGPL-3.0 的第三方作品，原样分发、未作修改，许可证见该目录。

这样"聚合分发"的边界是清楚的。代价仍然是：上游更新要自己跟。

## 六、上游作者怎么说的

`dsh-learnharness` 自己的 README 写的是：

> AGPL-3.0，与上游 LearnHarness 一致。

也就是说它明确选择了同一个许可。你**独立安装**它，和你**改它再发布**，是两件完全不同的事——
后者你的修改也必须 AGPL。
